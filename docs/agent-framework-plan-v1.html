01

不限定品类，统一预测流程

建议题目：基于证据溯源与多主体推演的通用事件预测 Agent 框架。项目暂名 ForecastLab。

用户拿它来做什么

学生或研究者输入一个现实事件问题，系统帮助搜索资料、分清事实与假设、模拟相关参与方的反应，最后形成有依据的预测报告。要解决的具体问题是“回答有结论，却查不到依据和推演过程”。

跨品类指入口和框架通用，不等于对所有问题都有同等预测能力。商业、科技、体育或公共事件都可以输入，系统先判断是否具备可预测的目标。

统一的是问题格式

每次明确：预测什么、截至何时、有哪些结果、怎样判断结果发生。有清楚结果的问题输出概率；“未来会怎样”等开放问题先请用户确认目标，或只输出情景分析。

对天气、纯随机事件等缺少战略主体的问题，可以跳过主体博弈，明确记录原因；避免为凑 Agent 数量虚构参与者。

概念依据：中科闻歌产品介绍；作者技术报告摘要索引。本节右列均为本项目设计，不是对官方内部实现的描述。

复现范围：已核实产品公开页面和可读取的作者摘要；技术报告原站访问受限，尚未核实全文算法、训练数据、模型权重和实现细节，也未确认可用的官方开源实现。因此题目宜用“Decitron-inspired”，暂不承诺论文结果复现。官方网页显示的“准确率”口径尚未独立核实，不作为我们的验收数字。

这份项目自己的贡献

把证据来源、事实与假设的区分、主体行动和预测版本连成可检查的工作流。用相同证据下的单 Agent 对照，验证这套流程是否更好用、更容易核查，并记录它的代价与局限。

03

一台电脑，四个组成部分

前端工作台、Python 后端、DeepSeek 模型、本地数据库。多个 Agent 是后端中的不同角色，无须部署多台服务器。

React 工作台

显示问题表单、证据表、主体说明、运行时间线、预测报告和历史回放。修改条件后创建新运行。浏览器只调用自己的 API；模型密钥留在服务端。

以上是本项目建议架构，不是 Decitron 内部架构图。首版同时运行 1 个预测任务，主体调用并发上限 3；前端轮询即可，不需要 WebSocket 或 SSE。

LangGraph 负责“谁先做、交给谁”

把流程写成明确步骤：整理问题 → 取证 → 建模 → 推演 → 审查 → 汇总。它负责流程控制，具体 Agent 通过同一个 DeepSeek 调用函数工作。

不再叠加 CrewAI、AutoGen 等第二套编排框架。首版只用 LangGraph 的基础状态图。

共享状态负责“大家读同一份资料”

RunState 保存问题、证据 ID、世界状态、行动记录、审查意见和结果。每个 Agent 只写自己负责的字段，所有阶段产物落盘供回放。

后台进程中断时标为 interrupted，让用户重跑；首版不承诺断点自动续算。

04

每个 Agent 只做好自己的事

所有角色共用一个 DeepSeek 模型。区别来自任务、能看到的资料、可用工具和必须交出的结果，不来自模型数量。

角色读什么 / 做什么交付什么不能做什么
① 问题定义 Agent读取用户问题，提取目标、时间和结果；判断能否直接预测。QuestionSpec：规范化问题、结果选项、结算规则、缺失信息。不能擅自补出有争议的时间或判断标准；缺项返回前端补充。
② 证据 Agent根据问题提出检索词；调用搜索工具，读取原始网页或导入资料。EvidencePack：带 URL、时间、原文片段的证据条目，以及冲突和缺口。不能把模型常识或搜索平台自动总结当作已核实资料；不能生成不存在的来源。
③ 世界建模 Agent读取问题与证据；梳理相关主体、目标、资源、约束和关键变量。WorldState + ActorProfile[]，每项区分事实与假设。不能把推测出的动机写成已知事实；不虚构精确收益函数。
④ 主体 Agent × 2–4每个实例代表一个相关参与方。读取自己的画像、可见证据和轮初状态，独立决定行动。ActorAction：行动、目的、依据、预期影响、适用条件。不能改共享世界状态，不能看其他主体本轮尚未提交的行动，不单独联网取证。
⑤ 环境推进器读取同一轮的全部行动和原状态，用 LLM 提出联合影响，再由代码检查。SimulationStep：冲突处理、模拟状态变化、理由与未解决问题。不能把模拟行动当作已经发生的新闻；不能声称是准确的通用因果模型。
⑥ 审查 Agent读取证据、世界状态与完整轨迹，检查遗漏、反证、引用错配和不合理跳跃。Review：问题清单、严重度、需删除的主张、缺失证据。不能为了达成共识掩盖分歧；不能自己制造新证据。
⑦ 预测汇总 Agent结合证据、模拟轨迹和审查意见，回答最初的问题。Forecast：概率、支持/反对理由、其他情景、局限及引用。不能用“两轮模拟成功一次”推出 50% 真实概率；不能把主观概率叫已校准结果。
工作 Agent 与主体 Agent：“证据 Agent”是研究助手；“某家企业 / 某个组织的主体 Agent”是模拟参与者。后者必须有自己的目标和行动，并通过环境推进器影响后续状态，才能体现多主体交互。

哪些事情交给普通代码

LangGraph 决定执行顺序；Pydantic 检查数据字段；来源检查器核对引用编号；后端限制调用次数；Python 计算评分。它们不必包装成会说话的 Agent。

多个角色不等于独立专家

同一模型的不同角色可能共享偏见。保留各自的行动和依据，审查证据是否真正支持结论；不把角色一致意见当作额外事实或高置信证明。

05

一次预测，从输入到可追查的报告

默认 3 个主体、2 轮模拟、1 次审查。没有适合的行动主体时走情景分析分支，并在结果中说明。

先把“预测什么”说清楚

例如用户问“这次产品发布会延期吗？”系统提取发布主体、当前承诺日期和“延期”的判定方式；缺失的信息交给用户确认。这里不限定产品、赛事、政策等品类。

输入：自然语言问题　→　输出：目标 + 截止时间 + 结果选项 + 判定依据

无法定义结果的开放问题，可继续做情景分析，但不硬给可评分的概率。

先有证据包，再开始推演

最多 3 次搜索，收集约 6–10 条有效证据。优先找原始公告和官方记录；对关键主张寻找独立来源或注明单一来源。保存原文，不只保存 AI 摘要。

输入：QuestionSpec　→　输出：EvidencePack（来源、片段、时间、冲突）

离线证据包也走相同接口，保证课堂网络出问题时能继续演示。

把事件画成一份小型“世界说明书”

识别关键主体、他们已知的目标与约束，整理当前状态。没有证据的动机必须标记为假设。对信息不足或没有战略参与者的问题，选择相应的分析分支。

输入：QuestionSpec + EvidencePack　→　输出：WorldState + ActorProfiles

不必搭建大型图数据库。一份有明确字段的 JSON 足够支持 Demo。

各自行动，再统一更新环境

每个主体独立读取 S₀ 并提出行动；环境推进器汇总后生成模拟状态 S₁。第二轮都从同一个 S₁ 出发。遇到相互冲突的行动，保留冲突与条件，不按调用先后默认谁成功。

S₀ → {A₁, A₂, A₃} → 模拟 S₁ → {A′₁, A′₂, A′₃} → 模拟 S₂

只模拟一条完整轨迹。报告中的其他情景属于文字对照；完整分支沙盘可以后续扩展。

检查“这句话凭什么成立”

先由代码查引用存在性、时间、字段和约束，再由审查 Agent 检查原文是否支持主张、模拟是否跳步、是否忽略反证。严重问题未解决就不给有效概率。

输入：证据 + 状态 + 行动 + 轨迹　→　输出：Review

只允许一次有范围的修复。修改上游状态会使下游结果失效；预算不够时返回部分结果，不悄悄沿用旧推演。

结论、依据和局限一起交付

明确回答目标问题，展示“主观概率 · 未校准”、支持与反对证据、模拟轨迹和可能改变结论的新信息。每条重要主张可点击展开原文与出处。

输入：有效阶段产物 + Review　→　Forecast　→　最终代码校验　→　报告导出

最终再次检查引用、概率与状态。汇总只能使用已审查主张，新增主张须重新审查或删除。证据不足或问题不可结算时，概率为 null，状态为 insufficient_evidence 或 scenario_only。

SAO 的课程版理解：
S：现在有什么事实与假设？
A：各参与方可能采取什么行动？
O：行动组合后，模拟世界发生什么变化？

一个说明性例子：供应商在模拟中延迟交货，企业选择改用备选供应商，监管方要求补充材料。环境推进器据此推演下一步，并引用这些行动和初始证据。这些行为是模型生成的可能情景，不是新发生的事实。跨品类 Demo 的重点是把这种区别始终保留下来。

06

证据来源，是这套框架的主线

任何读者都应能从报告中的一条结论，找到它使用的证据、假设与模拟过程。

三种内容分开存，也分开展示

类型内容示例来源要求在后续流程中的身份
E / 外部证据某机构公告里写了某个日期。真实 URL 或本地文件、原文片段、发布/更新时间、抓取时间。只证明“来源说了什么”；仍可能不实、过期或与其他来源冲突。
H / 建模假设预计企业优先控制成本；用户假设需求上升。记录由用户提出还是模型推测，写明理由与依赖证据。可修改的条件，不能包装成已核实事实。
M / 模拟结果模拟第二轮中企业选择延期发布。记录轮次、主体行动、父状态、依据与生成者。用于讨论可能后果；绝不回流成新的外部证据。
引用链：报告主张 → evidence_ids / assumption_ids / simulation_ids → 原文、假设或状态变化。报告中的 URL 从证据库查出来；不让汇总 Agent 自己自由编写网址。
  1. 唯一的资料入口

    证据 Agent 提出搜索请求，由后端工具执行。URL、快照、哈希和抓取时间由工具根据真实返回生成，模型只能归纳和引用，不能自由填写。保存搜索提供方、查询词和来源网页；模型 API 本身不等于互联网搜索。

  2. 来源有层级，转述不算多份独立证据

    优先公告、原始统计、官方赛事记录等一手来源，再补可靠报道。记录 source_type、原始发布方与 source_group；多家网站转发同一新闻稿只算同一证据根源。

  3. 原文与摘要并存

    搜索摘要只能作为线索。能取到正文就保存支持主张的原文片段和快照；只能得到片段时标为 snippet_only，不声称全文核实。人工导入资料同样记录标题、出处和时间。

  4. 时间边界可核对

    分别记录事件时间、发布时间、更新时间、抓取时间与预测的 as_of。历史测试使用截点前已冻结或可验证的历史快照；今天抓到的旧文章可能被改过，不能只凭早期发布日期当作历史证据。

  5. 冲突和缺口不会被“总结掉”

    两份资料相互矛盾时都保留，并给 conflict_group。无法核实日期、关键资料失效或只有单一低可信来源时，在报告中显示缺口；必要时不输出概率。

  6. 引用存在性与内容支持度分开检查

    代码能检查 E001 是否存在；审查 Agent 和抽样人工核查判断 E001 原文是否真正支持该句话。引用有效不等于事实正确，原始来源权威也不保证每项预测结论成立。

后端怎么跑任务

创建 run 后返回 ID，后台执行 LangGraph，前端每 2 秒请求当前阶段。每个阶段完成就写入 SQLite。限制同时 1 个 run，避免课堂演示时任务相互影响。

采用单 Uvicorn worker。重启后未完成任务标为 interrupted；“重新运行”创建新 run_id，历史记录不覆盖。

09

先证明流程可靠，再讨论预测好不好

课程需要可用性和评估证据。用一个小而清楚的测试集完成这件事，不为了数字好看挑选成功样例。

一组跨品类测试

建议准备 20–30 个问题，覆盖商业、科技、体育、公共事件等至少 3 类。选其中 6–10 个调试，余下固定为测试问题；同一事件的变体放在同一组。

这是探索性规模，不证明系统对所有品类都准确。记录每类样本数，避免只报一个掩盖差异的总分。

一项清楚的对照

单 Agent 与完整框架使用相同 DeepSeek 模型、相同问题、相同证据包。比较输出、引用质量、耗时和 token；有余力再加“去掉主体推演”的版本。

完整框架调用更多。若未匹配预算，结论只能是整套流程的效果比较；不能把提升全部归因于多 Agent 架构。

要验证什么怎么检查验收或记录
流程能否跑通从输入、证据到报告，测试正常输入、缺字段、搜索失败、API 超时和进程中断。所有预置 Demo 样例可完成；故障有明确状态和可检查日志。
引用是否可追查代码检查引用编号存在；人工抽查原文与主张是否对应。无不存在的引用 ID；分别记录来源可访问率与引用支持率。
事实有没有被模拟污染检查 H / M 类内容有没有被写回 E 类，检查每轮状态的父版本。自动检查全部通过；人工展示一个假设与真实事实的差别。
预测质量只对已有客观结算结果的事件算 Brier；记录结算来源、时间、规则。报告分数、有效样本数和拒答率；未结算事件只测流程。
投入是否合理记录每次调用 token、总耗时、实际账单或按当期价格估算。与单 Agent 并列展示；不把离线回放耗时算成生成速度。
用户是否能理解让 3–5 位同学完成“找到依据、识别假设、说明结论变化”任务。记录任务完成情况、卡住的位置和改动；避免仅问满意度。
二元事件：Brier = 平均值[(预测概率 p − 实际结果 y)²]
y 为 0 或 1；分数越低越好。使用 0–1 的二元定义；若扩展多选结果，另报多分类指标，不混合口径。

指标定义：scikit-learn Brier score 文档。第一版优先用跨品类“是否发生”的问题评分，入口仍支持开放问题进入情景分析。

展开：最容易影响实验结论的三个问题

历史答案污染：过滤检索时间不能阻止模型记住历史结果。回顾测试要注明这一局限；有时间就提前登记几条将在展示前结算的新问题，保存不可覆盖的预测时间和概率。

只统计成功样例：所有失败和拒答都保留。主表同时报告覆盖率；在共同成功样本比较之外，对已结算二元问题另报告固定 p=0.5 回退下的全样本 Brier，标清回退口径，避免筛掉困难题。

测试后调提示词：先固定提示词、模型配置和预算再跑测试；不能看到答案后修改规则，并用同一批题声称提升。样本少时只做初步比较，不拟合复杂校准器。

报告里必须保留的失败案例

至少展示一个证据相互矛盾的例子、一个主体假设不合理的例子，以及一个因证据不足而不输出概率的例子。解释原因和改进方向，与成功案例一起组成评估证据。
